## D1 — User-vs-group precedence (LOCKED)

| ID | Date | Decision | Type | Rationale | Evidence required to revisit (falsification) |
|----|------|----------|------|-----------|----------------------------------------------|
| **D1** | 2026-06-21 | **A group permission has less weight than a direct user permission — option (a), user precedence.** A direct `IRoleInUser` grant for `(userId, appRoleId)` is **authoritative**: when one exists, group grants for that role do not override it and `getGroupPermission` is not consulted, for all three `PermissionType` values including `Default` (a `Default` direct row resolves to `appRole.defaultPermission`). This **ratifies current behavior** (CONTRACT C2 → T5): the user-vs-group axis needs **no** Phase-2 change. Rejected: (b) group-fallback-on-`Default` and (c) composition — both would let a group grant influence a user who holds a direct row, contradicting the directive. | APPROVED | User directive (2026-06-21): "a group permission has less weight than a DIRECT user permission." Direct assignment is the most specific, highest-intent grant; letting a group override it is the surprise. Group grants remain fully in force for users with **no** direct row for that role — D1 narrows the multi-grant conflict question (D2) to the **intra-group** case only. | A concrete requirement that a **group-level** decision must override a direct user grant — e.g. a compliance/security lockout applied at the group level that no individual grant may override — which would need a separate hard-deny layer *above* direct user grants, not a change to this precedence. |

## D7–D9 — Group-aware SingleAction membership API (**LOCKED 2026-06-22**; **shipped P4**, `RbacMembership`)

> Motivated by R12/R13: a real Mongo consumer bypassed fsLib and went group-blind because there is
> no `(userId, appRoleId)`-keyed, group-aware, non-materializing boolean. These three decisions design
> that API. They **do not modify `permissionState`** — they add new operations; `isAllowedSingleAction`
> **inherits** the locked D1–D6 semantics where it performs authz, while `hasSingleActionGrant` is a
> non-authz existence helper that resolves no verdict.

| ID | Date | Decision (question + options) | Type | Rationale / recommendation | Falsification (if recommendation approved) |
|----|------|-------------------------------|------|----------------------------|--------------------------------------------|
| **D7** | — | **Two distinct `(userId/User, appRoleId)`-keyed Boolean operations** (closes the NEW-A ergonomic gap that drove the bypass), with **different, non-overlapping semantics** (see D8): **(1)** `hasSingleActionGrant` — pure existence union; **(2)** `isAllowedSingleAction` — effective authz. Reject folding either into a deny-override union that ignores D1 precedence. | **APPROVED — LOCKED 2026-06-22 (ship both); shipped P4** (`RbacMembership`) | Both are needed: the consumer wants a cheap membership boolean; an app gating an action wants the *authz* answer. Re-exposing them by `(userId, appRoleId)` → `Boolean` (not `ApplicationCall`/`UserSession` → `SimpleState`) is the actual ergonomic fix. | A consumer need for a single combined op — then pick one as the default and document the other as the explicit alternative; the two semantics still must not be blended into one verdict. |
| **D8** | — | **The two operations' semantics — and the D1-consistency constraint.** **(1) `hasSingleActionGrant`** = **pure existence union**: ∃ *any* grant edge (direct OR group), ignoring `permission`/defaults/`upVote`. Commutative; resolves no verdict, so D1 precedence is N/A. Matches the consumer's raw `countDocuments`. **(2) `isAllowedSingleAction`** = **effective authz = the D1/T5 precedence resolution restricted to SingleAction**: a direct grant is **authoritative** (resolve it: `Allow`/`Deny`/`Default`→default); groups are consulted **only when there is no direct row**, then by the D2 intra-group rule. So a direct `Allow` + group `Deny` is **`Allow`** under both `permissionState` and `isAllowedSingleAction` (consistent with T5). | **APPROVED — LOCKED 2026-06-22 (as stated); shipped P4** (`isAllowedSingleAction` **is** `RbacResolver.resolve(crudTask=null)`, pinned by `directAllowWithGroupDenyIsAllowedByPrecedenceNotUnion`) | **Corrects a prior contradiction:** an earlier draft made `isAllowedSingleAction` a deny-override union, which would have flipped a direct `Allow`+group `Deny` to `Deny` — a *second*, conflicting authorization semantic versus the locked D1/T5. Effective authz MUST equal the precedence resolution. Pure existence stays a separate, clearly-named helper that never claims to be an authz decision. | A genuine requirement for a **hard-deny layer that overrides even direct grants** — that would be a *new, explicit* layer above D1 (e.g. an org/group-level lockout), recorded as its own decision and a T5/D1 amendment, **not** smuggled into `isAllowedSingleAction`. |

Both sit over the **D5=c typed grant-fetch port** (a `Boolean`-only port can implement existence but **cannot** carry the permission/defaults/upVote that authz needs — so the port returns typed grant summaries, with a boolean/count fast path for existence). | **APPROVED — LOCKED 2026-06-22 (as stated); shipped P4.** Port gained the **required** `fetchAppRolePolicy` (no fail-closed `=null` default — consistent with the port's other 5 required methods and safe since the port is unreleased; a default would let an implementer silently deny-all authz by omission, the wrong posture for a security port). ## Refuted / non-decisions (kept to prevent rejection amnesia)

- **`hasSingleActionGrant` (pure existence) ≠ `isAllowedSingleAction` (effective authz).** Two distinct
  operations (D8), not one blended verdict. *Pure existence* is a commutative union that resolves no
  verdict, so it never lets a group grant "override" a direct one — it only reports an edge exists
  (`IRoleInUserColl.kt:205-234` is irrelevant to it). *Effective authz* **is** the D1/T5 precedence
  resolution (direct authoritative; groups only when no direct row) — it does not introduce any new
  precedence and therefore cannot contradict D1. An earlier draft wrongly defined effective authz as a
  deny-override *union* (a group `Deny` blocking a direct `Allow`); that is REJECTED as a second,
  conflicting authorization semantic. Verified in code (2026-06-21 review).

- **Group-based action assignment is NOT absent.** It is real and functional in Mongo
  (`getGroupPermission`, C3). The defect is reach (Mongo-only, R1), totality (R3/R4), and coverage
  (R8) — not existence. Do not re-scope this as "add group support"; it is "specify, decide, unify,
  and pin group support that already exists."
- **`upVoteInGroup` is not dead.** It works for the multi-group case; it is merely skipped for the
  single-group case and has an unsafe fall-through. D2 fixes the totality, not the concept — do not
  propose deleting the field without a D2 outcome that removes per-role bias entirely.
- **Mongo's `enforcesPermissions=false` in the existing conformance profile is not a Mongo bug.** It
  reflects that the harness drives `PermissionRegistry`, not `Coll.roleInUserColl` (the real engine)
  — [[repository-write-lifecycle]] D11. D5's resolution port is what lets the suite finally reach it.
