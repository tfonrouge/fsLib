# LEDGER — RBAC Permission Resolution

> Decisions recorded symmetrically. **D0** is settled (the process). **D1–D6 are OPEN** — this is the
> "first decision set to lock down." Each OPEN entry enumerates the options, marks one
> **Recommended**, and states the falsification condition that *would apply if the recommendation is
> approved*. Locking a decision means: pick an option, set Type to APPROVED (or REJECTED for the
> alternatives), and ensure the falsification condition is non-empty. Honor standing rejections;
> surface any approval whose falsification condition is later met.
>
> **Nothing in D1–D6 is implemented until it is locked** — and no semantic change lands before the
> Phase-1 characterization tests freeze current behavior (D0).

## D1–D6 — Open decision set (to lock down)

| ID | Date | Decision (question + options) | Type | Rationale / recommendation | Falsification (if recommendation approved) |
|----|------|-------------------------------|------|----------------------------|--------------------------------------------|
| **D1** | — | **User-vs-group precedence.** How does a direct `IRoleInUser` grant relate to group grants for the same role? **(a)** Direct override — any direct row wins, groups ignored *(current, C2)*. **(b)** Group fallback — direct row wins only when non-`Default`; a `Default` direct row falls through to groups. **(c) [Recommended]** Composition — collect the user's direct grants **and** all group grants into one applicable-grant set, then resolve by the D2 conflict rule; no silent shadowing. | OPEN (proposed: **c**) | Composition is the mainstream RBAC model (effective permission = union of direct + group grants) and it removes the "a stray `Default` direct row silently disables every group grant" surprise (R2). It also makes D2 the single place conflicts are decided, instead of precedence being an implicit second rule. (b) is the minimal fix; (a) is the status quo and should be an explicit REJECTED if not chosen. | A concrete requirement that a direct user assignment must be able to **suppress** a group grant in a way composition + D2 cannot express (e.g. a per-user exception that must beat a group grant of the opposite sign) — which would reintroduce precedence as a deliberate, documented rule rather than an accident. |
| **D2** | — | **Conflict rule** for the applicable-grant set (across groups, and — under D1c — across user+group). **(a)** Deny-wins (deny-override) globally. **(b)** Allow-wins globally. **(c)** Per-role bias via `upVoteInGroup`, made **total**: the bias direction wins if present among explicit grants; **else the opposite explicit grants win**; the role default applies **only** with zero explicit grants. **(d) [Recommended]** Deny-override as the global default **plus** `upVoteInGroup` retained as an explicit, documented per-role opt-in to allow-override — both made total per (c)'s "never discard explicit grants" rule. | OPEN (proposed: **d**) | Deny-override is the safe, conventional default for an authorization control; keeping `upVoteInGroup` as an *explicit* per-role escape preserves the existing data model's intent without the R4 foot-gun. The non-negotiable part (any option): **a present explicit grant is never silently replaced by the role default** (closes R4, satisfies T1). The single-group case must apply the same rule the multi-group case does (today it skips `upVote`, C3). | A role whose correct policy is genuinely most-permissive with **no** way to express a hard deny — i.e. evidence that global deny-override blocks a legitimate, intended allow that the per-role allow-override opt-in cannot reach. |
| **D3** | — | **`crudTaskSet`-miss semantics.** When a CRUD task is **not** in a grant's `crudTaskSet`: **(a)** the grant simply does not apply to that task — contributes nothing / `Deny`, **no inversion** *(matches the direct-row path)* **[Recommended]**. **(b)** keep the current default-path inversion (`Deny`-default + miss ⇒ `Allow`, C4). **(c)** introduce an explicit deny-list flag so "applies to all tasks except these" is opt-in and never accidental. | OPEN (proposed: **a**, with **c** available if a deny-list is genuinely needed) | The inversion (R3) is a security foot-gun and the two code paths already disagree; an allow-list reading of `crudTaskSet` ("the tasks this grant covers") is the least-surprising and makes the direct and default paths agree (T1). If a deny-list is ever required, model it explicitly (c) rather than as an emergent inversion. | A real downstream model that depends on the "all tasks except the listed ones" semantics for a role and cannot migrate to an explicit deny-list flag — then (c) is required and the migration must be called out as BREAKING. |
| **D4** | — | **May a permission check write `AppRole` rows?** **(a)** Yes — keep lazy `findOne ?: insert` provisioning *(current, C5)*. **(b) [Recommended]** No — resolution is side-effect-free (T3); `AppRole` rows are provisioned by an **explicit** path: at view/service/container **registration** time, or a migration/`ensureRoles()` step, modeled and gated. **(c)** Compromise — keep lazy provisioning but route it through a modeled, gated, change-logged write and catalogue it in the [[repository-write-lifecycle]] CONTRACT (extend I7). | OPEN (proposed: **b**) | A read-shaped authorization check that mutates persistent state is exactly the un-modeled write the lifecycle work set out to eliminate (R5). Registration-time provisioning is enumerable for CRUD roles (one per container × task) and for single-action roles (discoverable at wiring). (c) is the fallback if some roles are genuinely unknowable until first access. | Evidence that the set of roles is genuinely **dynamic / data-driven** and cannot be enumerated at registration or migration time — then (c) becomes necessary and the lazy write must be made idempotent, gated, logged, and contract-catalogued. |
| **D5** | — | **Backend boundary.** **(a)** Mongo-only RBAC — formally declare RBAC a Mongo feature; non-Mongo engines fail closed or declare non-enforcement (couples to D6). **(b)** Full agnostic resolution over the storage abstraction so every engine resolves natively. **(c) [Recommended]** Split: a pure, engine-agnostic **resolution algebra** (D1–D4 live here, in `core`/`fullstack`) over a thin per-engine **grant-fetch port** (`fetchUserGrants`, `fetchGroupGrants`); Mongo keeps its `$lookup` fast path *behind* that port. | OPEN (proposed: **c**) | (c) makes the algebra unit-testable with no DB and conformance-testable across engines (closes R8's structural impossibility), removes the cross-engine coupling and global-mutable registration side effect (R1/R10), and fixes the generic-type loss (R6) since the port returns typed grants, not a private projection. It does not force SQL/InMemory to reimplement the policy — only to fetch rows. (a) is acceptable only if non-Mongo RBAC is explicitly unsupported. | Evidence that resolution genuinely cannot meet a performance/scale target without engine-specific aggregation that an in-memory port can't match — then keep an engine-specialized resolver behind the same port interface, but the *algebra* (D1–D4) must still be shared and singly-specified. |
| **D6** | — | **Default when enforcement is unconfigured/unsupported** (surfaced by R7; extends the user's set). **(a)** Allow-all *(current — SQL null-provider and InMemory both fail open, C6)*. **(b) [Recommended]** Fail closed on protected paths unless the engine/deployment **explicitly** declares a permission-free mode (the samples/tests `enforcesPermissions=false` declaration). **(c)** Fail closed always; no permission-free mode. | OPEN (proposed: **b**) | A security control that silently allows when misconfigured is a fail-open default (R7). (b) keeps the legitimate samples/tests convenience but makes it an **explicit opt-out** rather than the silent default, satisfying T4. InMemory's Action path must also actually *call* the check (today it doesn't, C6) so the declaration is real. | A deployment that legitimately needs allow-all-by-default at the library layer (enforcement done entirely in a layer above) and for which an explicit one-line "permission-free" declaration is unacceptable ergonomics. |

## Refuted / non-decisions (kept to prevent rejection amnesia)

- **Group-based action assignment is NOT absent.** It is real and functional in Mongo
  (`getGroupPermission`, C3). The defect is reach (Mongo-only, R1), totality (R3/R4), and coverage
  (R8) — not existence. Do not re-scope this as "add group support"; it is "specify, decide, unify,
  and pin group support that already exists."
- **`upVoteInGroup` is not dead.** It works for the multi-group case; it is merely skipped for the
  single-group case and has an unsafe fall-through. D2 fixes the totality, not the concept — do not
  propose deleting the field without a D2 outcome that removes per-role bias entirely.
- **Mongo's `enforcesPermissions=false` in the existing conformance profile is not a Mongo bug.** It
  reflects that the harness drives `PermissionRegistry`, not `Coll.roleInUserColl` (the real engine)
  — [[repository-write-lifecycle]] D11. D5's resolution port is what lets the suite finally reach it.
